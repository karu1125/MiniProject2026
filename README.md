# Context-Aware Framework for Logistic Incident Reconstruction

A Python prototype for reconstructing logistics incidents from shipment evidence. The framework estimates a possible damage interval, evaluates candidate causes, maps that interval to shipment custody stages, and reports when the available evidence does not support a definitive conclusion.

> **Research status:** This repository contains a prototype evaluated on eight hand-authored simulated scenarios. The reported metrics describe only those scenarios. They are not evidence of validated performance on real shipments or unseen data.

## Overview

Logistics operations move goods through multiple stages, including manufacturing, transportation, port handling, shipping, warehousing, and delivery. Incidents such as handling impacts, packaging failures, securing failures, and temperature excursions may be discovered at a checkpoint later than the time at which they occurred.

Reconstructing an incident is difficult because evidence may be incomplete, inconsistent, generated by different sources, or recorded using clocks with different levels of accuracy. A single observation may also be consistent with more than one possible cause.

The **Context-Aware Framework for Logistic Incident Reconstruction** is a Python prototype that processes shipment evidence and produces an evidence-based assessment. Its pipeline combines:

1. Evidence credibility scoring.
2. Damage-time interval localization.
3. Competing-cause evaluation.
4. Custody-stage mapping.
5. Evidence-based assessment with unresolved outcomes.
6. SHA-256 evidence-record hashing and a hash-chained audit trail.

The framework is intended to support human investigation. It does not independently establish legal responsibility, prove negligence, or replace expert judgment.

## Problem and objectives

The project addresses the problem of reconstructing the likely time and context of a logistics incident when the available evidence is heterogeneous or uncertain.

The prototype aims to:

- Estimate a possible interval during which damage occurred.
- Score evidence using consistency, source reliability, temporal quality, and corroboration indicators.
- Compare candidate causes using predefined evidence-support rules.
- Identify custody stages that overlap the estimated damage interval.
- Present intermediate results and supporting/conflicting evidence summaries.
- Abstain from naming a cause or party when the implemented decision rules do not support a definitive assessment.
- Detect changes to hashed evidence-record content through integrity verification.

## Architecture

### Processing flow

The browser interface sends shipment data to the Python backend. The backend converts the JSON input into the framework's data models, runs the pipeline, and returns the assessment and intermediate outputs to the interface.

The processing modules are:

| Module | Implementation | Responsibility |

| JSON conversion and reporting | `framework/serialize.py` | Converts browser input, calls the pipeline, and prepares response data |

### High-level pipeline

1. Evidence records are represented using `EvidenceItem` objects.
2. Evidence records are hashed into the audit trail.
3. Credibility scores are calculated.
4. Damage localization estimates an interval.
5. Candidate causes are scored.
6. The estimated interval is compared with the custody timeline.
7. The assessment module determines whether to name a cause and/or party.
8. The final report summary is hashed into the audit trail.

The integrity mechanism and credibility mechanism address different questions. Credibility scoring evaluates evidence indicators used by the analysis. Hash verification checks whether the content included in a stored hash has changed since it was recorded.

The default weights are all `0.25`. The weights must sum to `1.0`. The resulting score is bounded to the interval \([0,1]\).

An evidence item is considered credible for downstream processing when:

\[
Q_i \geq \theta
\]

The default credibility threshold is `0.5`.

The four input indicators are supplied as part of the evidence data. The current prototype does not independently estimate source reliability from a live logistics system.

### 2. Damage localization

The initial interval is defined using credible inspection checkpoints:

\[
I_0 = [T_{\text{last good}}, T_{\text{first bad}}]
\]

- \(T_{\text{last good}}\) is the latest credible checkpoint reporting undamaged cargo.
- \(T_{\text{first bad}}\) is the earliest credible checkpoint reporting damaged cargo.

The implementation then:

1. Selects credible evidence using the credibility threshold.
2. Attempts to refine the checkpoint interval using checkpoint timestamps and clock-error margins.
3. Builds time windows around credible sensor anomalies using each item's clock-error margin.
4. Keeps an anomaly window only when it overlaps the clock-error window of an independent credible photograph or inspection note.
5. Intersects corroborated anomaly windows when they overlap. If the windows conflict, it falls back to the updated checkpoint interval.
6. Checks that the refined interval remains within the initial interval.

The output is an interval, not necessarily an exact incident timestamp. The current implementation assumes a single incident interval for a shipment.

**Implementation caveat:** The checkpoint-bound refinement currently does not effectively tighten the initial interval using the checkpoint clock-error values. The initial bounds are already set by the latest good and earliest bad checkpoint, and the subsequent max/min operations retain those bounds. Clock-error margins are used in the anomaly/photo-or-inspection corroboration windows. This behavior should be reviewed before claiming that checkpoint clock uncertainty is fully handled.

### 3. Competing-cause evaluation

The cause module uses a predefined support-value table for sensor anomalies, photographs, and inspection notes.

The implemented support values include:

- `+1.0`: strong support.
- `+0.5`: weaker support.
- `0.0`: no bearing.
- `-0.5`: weaker evidence against a cause.
- `-1.0`: strong evidence against a cause (available in the documented scale; the current rules do not assign this value).

For each cause \(c\), the implementation calculates a weighted support score:

\[
S_c = \frac{\sum_i Q_i s_{ic}}{\sum_i Q_i}
\]

Here, \(s_{ic}\) is the support value assigned to evidence item \(i\) for cause \(c\). The current implementation applies this calculation to credible evidence types handled by the support table. Evidence types without a support-table function do not contribute to this cause calculation.

The default minimum cause-support threshold is `0.3`. The default separation margin is `0.2`.

The decision logic is:

- If there is no informative credible evidence, the outcome is insufficient evidence.
- A cause must meet the minimum support threshold to qualify.
- If exactly one cause qualifies, it is selected as the leading cause.
- If multiple causes qualify, the top score must exceed the runner-up by at least the configured margin.
- Otherwise, the cause outcome is unresolved.

These scores are rule-based support scores. They are not calibrated probabilities.

### 4. Custody mapping

The custody module identifies all custody stages whose time ranges overlap the estimated damage interval.

If more than one stage overlaps the interval, the result is treated as crossing a handover. The assessment does not name one party solely because its custody period overlaps the interval.

An overlap is a candidate for investigation, not proof that the corresponding party caused the damage.

### 5. Evidence-based assessment

The assessment module combines localization, cause, and custody outputs.

The current confidence logic includes:

- **High:** A leading cause is available, one custody stage overlaps the interval, the cause score is at least `0.75`, and its margin over the runner-up is at least `0.4`.
- **Moderate:** A leading cause is available, but the interval crosses a handover or the cause evidence does not meet the high-confidence condition.
- **Low:** Localization is flagged/conflicting, or a leading cause exists without an overlapping custody record.
- **Unresolved:** The cause evaluation reports insufficient evidence or unresolved competing causes.

These are implementation-specific confidence categories, not statistically calibrated confidence probabilities.

### 6. Evidence integrity

The pipeline hashes each evidence item at collection time and records the hashes in an in-memory, hash-chained audit trail. It also records a hash for a small summary of the final assessment.

The standalone demonstration modifies a sensor record's payload after collection and verifies that the modified payload no longer matches its stored hash.

The current audit trail is an integrity demonstration. It is not persistent storage, and it is not independently anchored outside the running process.

## Installation and execution

### Prerequisites

- Python 3.10 or later.
- Visual Studio Code or another Python-compatible editor (optional).
- A modern web browser.

### Get the project

Clone the repository or download and extract the project ZIP.

```bash
git clone <repository-url>
cd logistics-framework
```

Replace `<repository-url>` with the actual Git repository URL.

### Verify Python

```bash
python --version
```

### Run the web application

From the project root:

```bash
python app.py
```

The server binds to `127.0.0.1` and normally starts at:

```text
http://127.0.0.1:8000
```

If the default port is occupied, the application tries subsequent ports. The selected address is printed in the terminal.

To choose a starting port:

```bash
python app.py 8080
```

To prevent the application from opening a browser automatically:

```bash
python app.py --no-browser
```

Stop the server with `Ctrl+C`.

### Run the evaluation

```bash
python evaluate.py
```

This runs the proposed framework and the three baseline methods on the eight simulated scenarios.

### Run the tamper-detection demonstration

```bash
python demo_tamper_detection.py
```

No additional package installation is required.

## Evaluation

### Evaluation design

The evaluation script compares the proposed framework with three baselines over the same eight simulated scenarios.

| Method | Implemented behavior |
|---|---|
| Proposed framework | Credibility scoring, interval localization, cause scoring, custody mapping, and assessment |
| First Bad Checkpoint | Uses the midpoint between the latest good checkpoint and earliest bad checkpoint, then maps that time to custody |
| Anomaly-Only Analysis | Selects the sensor anomaly with the largest raw magnitude and maps its timestamp to custody |
| Custody-Only Analysis | Uses the anomaly-only timestamp when available; otherwise uses the first-bad-checkpoint baseline time, then maps it to custody |

### Metrics and denominator notes

| Metric | How the current script calculates it |
|---|---|
| Median localization error | Median absolute difference between estimated midpoint and ground-truth damage time for scenarios with a ground-truth time and an estimated time |
| Interval coverage | Proportion of evaluated ground-truth damage times contained in the estimated interval |
| Average interval width | Mean estimated interval width; for the proposed method this includes all eight scenarios |
| Cause precision | Correct leading-cause predictions divided by scenarios where a leading cause was reported and ground-truth cause was available |
| Cause recall | Correct leading-cause predictions divided by all scenarios with a ground-truth cause |
| Cause F1 | Harmonic mean of the above pooled precision and recall; the current code variable is named `cause_macro_f1`, but this is **not macro-F1** |
| Custody attribution accuracy | Correct party predictions divided by cases where the method named a party and ground-truth party was available |
| False-attribution rate | Incorrect named-party predictions divided by all eight scenarios |
| Abstention rate | Proposed-framework scenarios whose assessment confidence is `unresolved` divided by eight |
| Audit-chain check | Whether the proposed framework's in-memory audit chain verifies for each scenario |

**Important interpretation:** The custody-accuracy metric excludes cases where the method did not name a party. The false-attribution metric does not penalize abstention or failure to name the correct party. Therefore, these two metrics must be read together with the number of named-party predictions. A low false-attribution rate alone does not establish strong attribution performance.

The current evaluation script does not calculate cause-classification metrics for the baselines.

### Reproducing the current run

Run:

```bash
python evaluate.py
```

The output includes per-scenario proposed-framework results and aggregate metrics for the four methods.

### Interpretation and cautions

- The proposed framework's median localization error is calculated over the five scenarios with a ground-truth damage time.
- Its interval coverage is 100% for those five ground-truth damage times.
- Its average interval width is calculated over all eight scenarios, including broad intervals in ambiguous cases.
- The proposed framework names a custody party in only one scenario. Its reported custody attribution accuracy is therefore `1/1`, not evidence of broad attribution reliability.
- Its false-attribution result is `0/8` under the script's definition. This metric does not penalize missed attributions or abstentions.
- The cause F1 value of `0.89` is the harmonic mean of pooled precision (`4/4`) and recall (`4/5`). It is not a class-wise macro-F1 score.
- The anomaly-only and custody-only baselines produce point intervals, which explains their zero interval widths in this evaluation.
- The audit result confirms that the generated in-memory chains verify. The separate tamper demonstration checks one modified evidence payload.

These results demonstrate behavior on the included scenarios only. They should not be described as real-world performance, independent test-set performance, or statistically validated generalization.

## Implementation caveats

The following points were identified by inspecting and executing the current source code. They should be addressed before making stronger research or security claims.

### 1. Cause F1 naming

`evaluate.py` stores the harmonic mean of pooled cause precision and recall in a field named `cause_macro_f1`. It does not calculate per-class F1 values and average them. The README therefore reports this as pooled precision/recall F1, not macro-F1. The variable and output label in the evaluation code should also be renamed or the metric should be replaced with a genuine macro-F1 calculation.

### 2. Custody accuracy has a very small denominator

The proposed framework names a party in only one of the eight scenarios. Its custody attribution accuracy is `1/1`. Report the denominator whenever presenting this value, and consider reporting coverage (the proportion of eligible cases in which a party was named) alongside accuracy.

### 3. False-attribution rate does not measure missed attribution

The current calculation counts wrong named parties, divided by all eight scenarios. It does not count cases where the framework abstains or fails to name the correct party. Consider reporting false-attribution rate among named attributions as an additional metric, along with attribution coverage and missed-attribution rate.

### 4. Checkpoint clock-error refinement

The current checkpoint refinement operations do not effectively tighten the initial interval using checkpoint clock-error margins. Review the bound calculations and define the intended temporal semantics before claiming that checkpoint clock errors are fully incorporated into localization.

### 5. Audit hashes do not cover every analysis field

In `framework/pipeline.py`, the evidence hash payload currently includes:

- Evidence type.
- Timestamp.
- Source.
- Evidence payload.

It does **not** include all fields that influence the analysis, including clock-error minutes, consistency, reliability, temporal quality, and corroboration. A change to one of those omitted fields would not be detected by the current record-hash check.

The final report hash also covers only confidence, named cause, and named party, not the complete report or all intermediate results. Expand the hashed payload before describing the audit trail as protecting the complete evidence and assessment record.

### 6. Audit trail is in-memory

The hash chain is held in memory and is not independently anchored or persisted. It demonstrates hash and chain verification in the running prototype, but it is not a production-grade immutable or independently verifiable evidence store.

### 7. Simulated evidence indicators

The consistency, reliability, temporal-quality, and corroboration indicators are supplied as scenario/input values. The prototype does not yet establish these values from independently verified operational source histories.

## Limitations and future work

The main limitations of the current prototype are:

1. The evaluation contains only eight hand-authored simulated scenarios.
2. The cause-support table is rule-based and has not been validated on a large independent dataset.
3. The evaluation does not use separate development, calibration, and held-out test datasets.
4. The credibility indicators and default weights require independent calibration.
5. Checkpoint clock-error refinement requires technical review.
6. The audit trail is in-memory and does not hash every field used by the analysis.
7. Custody overlap is not proof of fault or legal responsibility.
8. The current evaluation does not report baseline cause-classification metrics or a true macro-F1.

Potential future work includes:

- Generating a larger randomized scenario dataset.
- Separating development, calibration, and test scenarios.
- Evaluating on appropriately governed real logistics data with independently established ground truth.
- Calibrating credibility weights and decision thresholds using a separate calibration set.
- Improving temporal uncertainty handling and testing it against known timestamp errors.
- Reporting per-class precision, recall, and F1, plus confusion matrices.
- Reporting attribution coverage and selective risk alongside abstention and false-attribution rates.
- Hashing every input field that affects the analysis and the complete assessment output.
- Persisting audit records in durable, access-controlled, append-only storage with an independent trust anchor.


## Reflection
The biggest technical hurdle I solved during this project was integrating multiple evidence-processing modules into a single incident reconstruction pipeline while ensuring that each module contributed meaningfully to the final result. Initially, evidence collection, credibility assessment, damage localization, cause evaluation, and custody mapping could be treated as separate tasks. However, connecting their outputs required careful data modeling and consistent interfaces between modules.

Another important challenge was handling uncertainty. A system that always identifies a cause or responsible party can produce misleading conclusions when evidence is incomplete or conflicting. I addressed this by implementing credibility thresholds, interval refinement, competing-cause evaluation, and abstention rules. These mechanisms allow the framework to produce an unresolved assessment when the available evidence is insufficient.

Implementing SHA-256 hashing and an audit trail also helped me understand the difference between evidence integrity and evidence credibility. Through this project, I gained practical experience in modular software architecture, Python backend development, mathematical reasoning, and systematic evaluation. The project also taught me the importance of testing assumptions and clearly communicating the limitations of simulated results.
